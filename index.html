A plain-language guide

Teaching a computer to recognize spoken medical terms by their sound

This project builds a searchable library of medical-term pronunciations. When someone says a drug or condition name out loud, the system compares the sound itself against that library and suggests the most likely terms — for a human to review.

💡 Think of it like Shazam — but instead of naming a song, it names the medical term it just heard.
Why this exists

Voice typing mishears medical words — and that can matter

When doctors or patients dictate notes, speech-to-text software often guesses wrong on uncommon medical names. The text it produces may look plausible while pointing to the wrong word entirely. In healthcare, a wrong drug name is not a harmless typo.

The speaker actually said
“metformin”

a common diabetes medication

➜
Speech-to-text wrote down
“met for men”

nonsense — the real term is lost

The key insight: even when the text is wrong, the original sound still contains the true pronunciation. This project listens to that sound as a second source of evidence — like asking a bystander “what did you hear?” after the first person wrote it down wrong.
The big idea

Three ingredients, one careful search

Everything in the project serves a single flow: build a trusted dictionary, give each term a reference “voice,” then compare new recordings against those voices.

1

A curated medical dictionary

Not paragraphs of medical advice — a tidy, version-controlled list of terms. Each entry has an official name, alternative names (aliases), a language tag, and a record of where it came from and whether a human has reviewed it.

2

Reference recordings of each term

Every term gets one or more short audio clips of how it sounds — either approved human recordings or clearly-labeled synthetic (computer-generated) speech. Different voices and accents can all point to the same term.

3

Sound comparison by numbers

A speech model converts every clip — references and new queries alike — into a list of numbers (an “embedding”). Clips that sound alike end up with similar numbers, so finding a match becomes measuring which numbers are closest.

Important: the system never decides anything on its own. It produces a ranked list of candidates plus the evidence behind each one, and a human reviewer makes the final call. If the evidence is weak, the system says “I don’t know” (abstains) rather than guessing.

The workflow

How the pipeline works, step by step

The full system is being built in six phases. Each phase below is explained in plain language, with a badge showing how far along it is.

📚

Phase 1 — Build and freeze the dictionary

Gather official medical vocabularies, check the files haven’t been tampered with, and tidy every term into a clean database.

Each source (e.g., MeSH, Orphadata, France’s BDPM drug database, a small Wikidata set) is downloaded, verified with a checksum — a digital fingerprint — and stored with its version and license. Nothing is silently merged: two terms that merely look similar stay separate. The result is a frozen, reproducible snapshot, so everyone can tell exactly which dictionary version produced an answer.

✓ Built
🎙️

Phase 2 — Give every term a voice

Create one short, isolated pronunciation clip for each term — a computer voice to start, human recordings where approved.

Synthetic speech is a practical way to cover tens of thousands of terms, but a computer voice can mispronounce medical names. So every synthetic clip stays labeled “synthetic” and must pass a pronunciation review before it’s trusted. The exact voice model and settings are pinned down and recorded, so a clip can always be reproduced — and failed generations are listed openly rather than hidden inside a “completed” batch.

✓ Built
🔢

Phase 3 — Turn sound into searchable numbers

Feed every reference clip through the same speech model and store the resulting “fingerprint” of numbers in a searchable index.

Each clip is converted to a standard format (16 kHz, single channel), checked for silence or defects, then encoded by a pretrained speech model (XLS-R) into a 2,048-number fingerprint. Every index is bound to the exact model version and settings that created it — a query encoded differently is rejected, because fingerprints from different recipes can’t be compared.

✓ Built
🔍

Phase 4 — Search with a new recording

Take a short query clip, turn it into numbers with the identical recipe, and find the closest-sounding reference clips.

For a single, isolated word this already works today. For longer recordings (like a dictated consultation), the plan is to first locate the moments where a medical term was probably said — using the transcript’s timing as a hint, while keeping the original audio and its exact time span — then search each of those short segments. Sound-alike matches survive even when the transcript spelled the term completely wrong.

✓ Single-clip search built → Finding terms inside long recordings: planned
🧩

Phase 5 — Combine sound evidence with text evidence

Merge the “what it sounded like” candidates with the “what the transcript said” candidates into one ranked, explainable list.

Sound scores and text scores speak different languages, so they can’t simply be added together — the project requires a documented, tested method for combining them, frozen before final evaluation. The reviewer sees every ingredient separately: sound similarity, matched pronunciation, text evidence, confidence, and the reasons behind each suggestion. If nothing is convincing, the system abstains or flags the item for human review — it never auto-fills an answer.

→ Planned
📏

Phase 6 — Measure honestly, then improve

Test on fresh voices, noisy rooms, tricky sound-alike drug names, and recordings of people saying nothing medical at all.

The evaluation set uses speakers the system has never trained on, includes deliberately confusable pairs and out-of-dictionary speech, and measures both “did it find the right term?” and “did it correctly stay silent when there was no term to find?”. An experimental technique that compresses the fingerprint into a smaller, sharper form (a trained 256-number projection) exists, but it only replaces the baseline if these measurements prove it better.

◐ Experimental improver built, not yet proven → Full evaluation: planned

Where things stand

What’s built today vs. what’s still planned

The document is careful to separate working software from ideas on the roadmap. Here is the honest scoreboard.

✅ Working today

  • Verified, version-controlled medical dictionary (SQLite database + exports)
  • Text search over term labels and spellings
  • Batch generation of synthetic pronunciation clips, with failure tracking
  • Sound-fingerprint encoding and the searchable audio index
  • Searching the index with a single, isolated spoken clip
  • “Abstain” behavior when filtering leaves no candidates

🛠️ Not built yet / not proven

  • Finding medical terms inside long, continuous recordings
  • Combining sound and text evidence into one ranked list
  • Reliably saying “no match” to unrelated speech using score thresholds
  • Proof that the experimental compressed fingerprint actually improves results
  • The existing web API route using the audio index (it currently only uses text)
  • Any claim of clinical or medication-safety validation
Safety principles

Designed to assist, never to decide

Because mistakes with drug names can cause real harm, the whole pipeline is built around caution. Four rules run through every phase.

🧑‍⚖️

A human always decides

The output is advice for a reviewer, never an automatic correction. The original recording and transcript are always preserved untouched, and the system is configured so it cannot write its suggestions back into any record (auto_commit_enabled = false).

✋

“I don’t know” is a valid answer

When evidence is weak, ambiguous, or the speech isn’t medical at all, the system abstains or flags for review rather than forcing a guess. Look-alike/sound-alike (LASA) drug names and low-confidence matches get extra scrutiny.

🧾

Every answer is auditable

Each suggestion carries its evidence: which reference clips matched, the sound and text scores separately, where in the recording the term was heard, and exactly which dictionary and index versions were used — so a reviewer can retrace every step.

🚫

No medical claims

This is a reviewer-assistance prototype for terminology lookup. It does not diagnose, prescribe, or establish medication safety — and context like a diagnosis or dose can never invent a drug candidate out of thin air.

Jargon buster

The technical words, translated

Every specialized term in the original document, in one sentence each.

Audio embedding
A list of numbers that captures what a sound clip sounds like — its mathematical fingerprint.
Cosine similarity
A score for how alike two fingerprints are — like measuring whether two arrows point the same direction.
RAG (retrieval-augmented generation)
Here it just means “look things up in a controlled dictionary first” — no AI text-writing involved in this project.
ASR (automatic speech recognition)
Speech-to-text software — the thing that heard “met for men.”
TTS (text-to-speech)
The reverse: a computer voice that reads terms aloud to create reference recordings.
Vector index
A filing cabinet for number-fingerprints, organized so the most similar ones can be found fast.
XLS-R / wav2vec2
The off-the-shelf speech model used to create the fingerprints; it was trained on many languages, but not specifically on medical terms.
Concept ID
The dictionary’s stable ID number for a medical term — the bridge that links a sound match back to an official entry.
Alias
An alternative name for the same concept (a brand name vs. a generic name, or the same term in another language).
LASA terms
“Look-alike, sound-alike” drug names — pairs like Celebrex / Celexa that are dangerously easy to confuse.
Abstain
The system’s way of saying “the evidence isn’t good enough — a human should look at this.”
Recall@5 / @20
A test score: how often the correct term appears in the top 5 (or top 20) suggestions.
Checksum / SHA-256
A digital fingerprint of a file, used to prove a download or recording hasn’t changed or been corrupted.
Pooling & 2,048-D
Summarizing a whole clip’s second-by-second features into one fixed list of 2,048 numbers.
Held-out test set
Recordings kept in a locked drawer during development, used only for final, honest scoring.
